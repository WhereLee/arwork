# 现场巡检问题标注

园区巡检人员在手机上用 AR 放置标记并上报问题，系统自动判定该派给哪一类修复者，修复者处理完由管理员验收。

三端：Unity（AR 采集 + 现场处理）→ Go（API + SQLite + AI 分派）→ React（工单管理 + 人员管理），共用同一个后端和同一份数据。

**在线演示**：<http://124.223.36.154:9400>（Docker 部署在云服务器）

## 启动

### 方式一：本地三端

**1. Go 后端**

```bash
cd server
cp .env.example .env        # 然后把 DEEPSEEK_API_KEY 填上，不填也能跑
go mod download
go run .
```

默认监听 `:8080`，数据库 `server/data/issues.db`，首次启动自动建表并写入演示账号。

`.env` 里的配置项：

| 键 | 说明 |
|---|---|
| `DEEPSEEK_API_KEY` | 留空则跳过 AI，所有工单走人工派单 |
| `DEEPSEEK_BASE_URL` | 默认 `https://api.deepseek.com` |
| `DEEPSEEK_MODEL` | 默认 `deepseek-flash` |
| `AI_CONFIDENCE_THRESHOLD` | 置信度低于此值转人工，默认 0.7 |
| `AI_TIMEOUT_SECONDS` | 单次调用超时，默认 8 秒 |

进程环境变量优先于 `.env`，所以部署时直接注入环境变量即可。

**2. React 管理端**

```bash
cd web
npm install
npm run dev
```

打开 `http://localhost:5173`，前端直连 `http://localhost:8080`，靠后端 CORS 放行。

**3. Unity AR 端**

用 Unity Hub 以 **2022.3.61f1c1** 打开 `unity/` 目录。

构建前确认 `Project Settings → XR Plug-in Management → Android` 里 **ARCore** 已勾选。这个配置必须由界面勾选生成，脚本重建不生效。

菜单：`ARWork / 1. 生成巡检场景` → `ARWork / 2. 构建 APK`，输出到 `unity/Builds/arwork.apk`。

### 方式二：Docker 部署

镜像分两个：`api`（alpine + 交叉编译好的 Go 二进制）和 `web`（nginx + React 产物）。只有 `web` 对外，`api` 走 compose 内部网络。

```
浏览器 ──9400──> arwork-web (nginx)
                    │ /api/    反代
                    │ /api/ws  WebSocket
                    └────────> arwork-api (容器内 8080，不出网)
                                  └── arwork-data (命名卷，存 SQLite)
```

一键部署（脚本在 `deploy/`）：

```powershell
.\deploy\deploy.ps1
```

脚本做六件事：交叉编译 linux/amd64 二进制 → 构建前端（`VITE_API_BASE=/api`）→ 打包上传 → 服务器 `docker compose up -d --build` → 健康检查。

为什么不在镜像里编译：服务器下行只有 3Mbps，拉 `golang` 基础镜像要七分钟；改成本地交叉编译再 `COPY` 二进制，构建是秒级的。

**关键点**：SQLite 文件挂在命名卷 `arwork-data` 上，跟容器生命周期分开。重启、重建容器、重新部署都不会丢数据，只有 `docker compose down -v` 才会删。

nginx 侧有两处配置不能少：`/api/ws` 的 upgrade 头、`proxy_read_timeout 3600s`。

## 工单流转

状态一共四个：

```
未处理 open
   ├─ AI 自动派单 ────────→ 处理中 in_progress
   ├─ 管理员人工派单 ──────→ 处理中
   └─ 管理员关闭（误报）──→ 已解决 resolved

处理中
   ├─ 修复者提交处理记录 ──→ 待确认 pending_review
   ├─ 修复者退回 ─────────→ 未处理（记退回）
   ├─ 管理员改派 ─────────→ 处理中（记改派）
   └─ 管理员强制关闭 ─────→ 已解决

待确认
   ├─ 修复者撤回 ─────────→ 处理中
   ├─ 管理员确认 ─────────→ 已解决
   └─ 管理员驳回 ─────────→ 处理中（记驳回原因）

已解决
   └─ 管理员重开 ─────────→ 处理中
```

**`pending_review` 是题面三态之外的扩展。**题面 §3.2 只要求 `open / in_progress / resolved` 三态；但修复者交活与管理员验收之间需要一个可区分的中间态，否则管理端分不清"还在修"和"修完了等我"。三个原有状态的行为没有变化。

所有状态变更都写进 `issue_events` 表，记录谁、什么时候、从什么状态到什么状态、什么原因。改状态用条件更新（`WHERE status = 期望值`），并发冲突返回 409，不会出现两个请求互相覆盖。

## AI 分派

巡检员提交后同步调一次 DeepSeek，让它判断两件事：这条工单属于哪一类、有多大把握。

```json
{"category":"device","canDispatch":true,"confidence":0.82,"reason":"标题提到门禁读卡器无响应"}
```

判得出且置信度过阈值，就在这个类别里按「当前负载少 → 同类历史上退回少 → 用户名」选一个人，直接派单并把状态改成处理中。判不出、没把握、或者这个类别暂无可用修复者，工单留在未处理，事件流里写一条 `ai_failed` 说明原因，等管理员人工派单。

**AI 的任何失败都不影响上报本身。**超时、接口报错、返回不是合法 JSON、字段越界，统一降级为人工派单。没配 `DEEPSEEK_API_KEY` 时整条链路退化为全人工，功能完整可用。

修复者提交处理记录后，会再调一次模型把自然语言整理成结构化 JSON（动作、结果、备件、跟进事项），存进 `repairSummary`。这一步失败不影响提交，原文已经在 `repairNote` 里。

实测线上一次分诊耗时约 **1.1 秒**（不是 8 秒的超时上限），因此没有做异步派单——异步会让"提交后立刻看到 AI 结果"变成"要刷新才看到"。

## 实时更新

网页端通过 WebSocket 订阅工单变化：别人改了一条，列表会自己刷新，不用点按钮。页脚有状态指示（实时 / 连接中 / 已断开）。

设计上**只推「有东西变了」不推内容**：三个角色能看到的工单范围不同，推内容就得按人过滤；推一个空壳让客户端按原有权限重新拉取，既不会串数据，代码也少一半。

- 鉴权：`/ws?token=xxx`（浏览器不能给 WebSocket 设自定义请求头）
- 心跳：服务端每 25 秒 ping 一次，比 nginx 默认 60 秒读超时短
- 断线：前端指数退避重连（1s → 15s 封顶）
- 背压：某个客户端积压 3 条还没消化就断开让它重连，广播绝不阻塞

Unity 端没有接 WebSocket（`UnityWebRequest` 不支持流式），用的是手动刷新。

## 接口

| 方法 | 路径 | 权限 | 说明 |
|---|---|---|---|
| GET | `/health` | 公开 | 服务状态，会检查数据库连通性，库不可用返回 503 |
| POST | `/login` | 公开 | 登录，返回 token 与角色 |
| GET | `/ws` | 登录 | WebSocket，订阅工单变更 |
| POST | `/issues` | 巡检员、管理员 | 新建工单，自动触发 AI 分派 |
| GET | `/issues` | 全部 | 巡检员看自己的、修复者看派给自己的、管理员看全部 |
| GET | `/issues/{id}` | 按角色 | 工单详情 + 全部留痕 |
| POST | `/issues/{id}/actions` | 按动作 | 工单流转，见下表 |
| PATCH | `/issues/{id}/status` | 管理员 | 直接改状态，受状态机约束 |
| GET | `/users` | 管理员 | 账号列表（含技能与手头工单数） |
| POST | `/users` | 管理员 | 新建账号 |
| PATCH | `/users/{username}` | 管理员 | 改技能、启停用 |

`POST /issues/{id}/actions` 的 `action` 取值：`dispatch`（派单/改派）、`return`、`submit`、`withdraw`、`approve`、`reject`、`reopen`、`close`。

错误统一返回 `{"error": "中文原因"}`：

- `400` 参数错误、必填项缺失
- `401` 未登录或 token 失效
- `403` 角色不对，或这条工单不在你名下
- `404` 工单或账号不存在
- `409` 冲突：当前状态不允许该动作、并发被别人改过，或用户名重复

## 三端操作流程

**巡检员（Unity）**：登录 → 选水平面或垂直面 → 扫平面 → 对准后点屏幕放置警示牌 → 填表提交 → 在「我的上报」里看状态 → 右上角「退出」可以切账号。

**修复者（Unity）**：登录后直接落在「派给我的」列表 → 点开工单看标题、描述、位置、上报人、流转时间线 → 现场处理完点「完成」写处理记录，或发现不归自己管点「退回」写原因。提交后如果反悔可以「撤回」。

**管理员（网页）**：工单表格里待派单的行有浅黄底色 → 点行打开抽屉，看基本信息和流转时间线 → 按当前状态派单、改派、验收、驳回、关闭或重开 → 「人员」页管理账号和技能。

### 工程化

- **部署**：双镜像 Docker，api 不出网、只暴露一个端口，SQLite 挂命名卷（重启不丢数据）；镜像不在容器里编译，服务器下行只有 3Mbps
- **测试**：Go **28 个用例**（状态机 19 种非法组合、CAS 陈旧快照、四协程并发只成功一次、AI 降级）+ React 3 个组件用例
- **CI**：Go（vet → test → build）+ React（test → build），两边都跑测试
- **可配置**：AI 的 key、模型、置信度阈值、超时全走 `.env`，不填 key 就全人工，功能不减

## 已知问题

**平台与硬件限制**

- **垂直面检测依赖墙面纹理**，白墙和玻璃大概率检测不出来，这是 ARCore 的平台限制。
- **ARCore 对光线敏感**。环境太暗会报 `InsufficientLight`，平面检测不出来——代码把这个状态翻译成了中文提示。
- **只打了 arm64-v8a 一个架构**。APK 17.7 MB（解压后 57 MB），没做多架构打包，老设备装不上。

**工程上的取舍**

- **CORS 设成 `*`**。现在走同源反代其实不需要 CORS，但代码里还留着放行配置，只适合演示环境。
- **登录态只有 12 小时自然过期**，没有失败次数限制和主动吊销。
- **WebSocket 是单进程连接池**。将来水平扩容需要接 Redis 发布订阅。
- **AI 分诊不缓存**。同一条描述重复上报会重复调模型。

**使用注意**

- **演示前需要清数据**。线上库是持久的，反复演示会积累测试工单。
